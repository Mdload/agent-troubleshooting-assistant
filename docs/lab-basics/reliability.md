# 可靠性学习资料

公开资料整理与核对：2026-10-21。只解释一般原理；没有读取任何实验室配置或设备。

## Keepalived配置阅读与切换条件

用途：离线阅读已有配置，区分业务探测、故障判定、VRRP选举与角色回调，不直接操作设备。

实例角色：`state MASTER/BACKUP` 指定初始状态，不是永久主备身份；`priority` 是参与VRRP比较的基础优先级，跟踪项可以影响有效优先级或导致FAULT。运行角色还受对端通告、候选状态及抢占设置影响。成为MASTER并持有VIP，也不等于应用已正确启用、已有连接保持或端到端业务已验证。

基础概念：先看启动参数是否用 `-f` 指定配置，常见默认文件为 `/etc/keepalived/keepalived.conf`，还要跟进 `include`。`vrrp_script` 定义脚本和 `interval/timeout/fall/rise/weight`，`vrrp_instance` 中的 `track_script` 才将它关联到实例；脚本正文决定检查进程、端口还是实际业务。`track_process` 属于进程跟踪，不等于验证业务响应。

只读起点示例（由用户自行按实际系统核对，助手没有执行）：
```sh
systemctl cat keepalived
systemctl show keepalived -p ExecStart
sed -n '1,200p' /etc/keepalived/keepalived.conf
```
先从前两项确认真实启动参数，再读取对应文件及引用脚本的正文；不要运行健康脚本或角色回调来“查看”，它们可能改变状态。

判断：`fall` 是连续失败达到脚本故障状态的次数，不是切换次数。零权重跟踪通常使相关实例进入FAULT；非零权重按符号及覆盖配置影响有效优先级，须核对 `track_script` 的权重/reverse、实例 `priority`、抢占设置及对端资格，不能只见失败就断言接管。`notify_master/notify_backup/notify_fault` 是角色转换回调；VIP归属由VRRP状态机管理，不应把回调笼统说成选举或降权主体。自定义回调还可能做其他动作，需读实现。

脚本判定：Keepalived读取检查脚本的退出码，不是它打印的“正常/失败”文字。还要确认脚本将真实失败正确传成非零退出码；末尾打印或另一条成功命令可能掩盖前面的失败。只连上端口或执行过一次 `curl` 不代表业务可用。curl默认不因HTTP错误状态码失败；`--fail` 能识别许多HTTP错误，但不能证明返回体中的业务结果正确。应按要验证的业务检查必要响应内容及依赖，区分探测范围与端到端业务，超时也须有界。

阅读算例（自拟、非部署配置）：假设主节点基础优先级110，健康备节点100，只有主节点的业务检查失败，且没有权重覆盖或reverse。`weight -20` 时主节点变为90，90低于100；对端还需具备接管资格、通告和抢占条件，不能只凭大小关系承诺接管。改成 `weight 0` 则是跟踪故障导致实例FAULT的路线。此处负权重例子不能概括所有非零权重：正权重在检查成功时加权，检查失效会失去这份加权，具体仍以跟踪配置为准。

常见问题：`fall × interval` 不能当实测切换耗时；配置也不能证明当前角色、业务不中断或既有连接保持。想判断实际接管，还需双方状态、通告和业务验证；本章不提供这些现场证据。

参考：[Keepalived配置手册的VRRP脚本与实例章节](https://www.keepalived.org/documentation/keepalived-conf/)、[Keepalived启动参数与默认配置位置](https://www.keepalived.org/documentation/user-guide/programs-synopsis/)、[curl手册的HTTP失败处理](https://curl.se/docs/manpage.html#-f)。分别支持跟踪/退出码/权重/回调、配置入口和HTTP返回码处理；HTTP传输成功不能独立证明业务逻辑正确，版本差异以实际安装版本手册为准。

## 工具超时与重试补偿边界

用途：设计Agent工具调用失败后的有限重试与结果核对，不把超时直接当未执行，也不自动重启或撤销操作。

基础概念：分清“确定未发出”“已完成”“结果未知”。只读或已确认具有幂等语义的操作，可在次数、总时限和退避预算内重试；操作已执行但响应丢失时，盲目重试写入或重启会重复产生副作用。请求ID只有在服务端落实去重、参数匹配及有效期规则时才是幂等保证，不能只加一个ID就宣布安全。

错误信息与执行状态：第三方返回“参数不合法”“失败”等文字，不足以证明零副作用。只有接口契约或可核对证据保证校验发生在任何副作用之前，才可归为“确定拒绝且无副作用”；这不同于“确定未发出”，因为请求可能已经发送并被拒绝。无法排除部分执行时仍是结果未知。错误类型用于选择下一步，不能代替执行记录或契约保证。

核对方法：保存本次请求/任务记录，关联操作目标、请求ID、进程启动时间和日志。服务为active只描述当前状态，不能证明对应重启请求完成。有限次核对仍不足时落盘标记未确认，停止依赖成功结果的后续动作，进入对账或人工处理；不伪造成功、失败或无限等待。

查询限制：一次“任务不存在”也可能来自排队、尚未入库或查询视图滞后；没有能排除原请求继续执行的服务端保障时，不能据此换ID重新提交。请求ID和操作状态由宿主绑定、持久化及校验；结果未知时只开放核对等允许动作，模型换ID也不能绕过原操作的约束。仅在提示里写“不要重复提交”不足以实现去重。

补偿边界：先确认哪些效果属于本次操作，再按业务规则、版本条件及授权执行可补偿步骤。补偿不一定恢复原状态，不能覆盖并发的新变更；结果未知时不自动反向操作。补偿本身也可能失败，需记录进度，并设计可重入/幂等处理及无法恢复的出口。重复重启可能断开连接或重放启动任务，不是一般意义上的无副作用操作。

常见问题：RFC的HTTP重试规则不能直接证明任意工具幂等；Stripe的服务端保障只适用于其相应接口；微软的补偿模式不承诺任何未知操作都能回滚。三者分别支持下列具体原则，不应拼成普遍安全保证。

参考：[RFC 9110第9.2.2节：HTTP幂等方法与自动重试条件](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)、[Stripe：服务端幂等键、参数检查与有效期](https://docs.stripe.com/api/idempotent_requests)、[微软补偿事务模式：并发、业务规则与失败恢复](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)。这些链接在资料整理时核对，不代表助手在每次回答中都重新联网。
